# Host deployment, confirmation and invoked maintenance

Deployment builds an identified artifact from the actual accepted integrated source, then uses the ticket's explicit adapter/target scope. `release-admit` requires build/deploy authority, successful build identity, matching integrated revision, component claim/fence IDs and each declared unit's configuration/binding/evidence locator. It does not run a default project or claim a deployment occurred. The host demo uses mode demo explicitly. Production qualification remains a separate capability; missing production infrastructure cannot silently upgrade the demo.

`release-rollout` records actual adapter readbacks with stable callback identity and monotonic unit sequence. Reject undeclared units and artifact/config substitutions. Identical callbacks are idempotent; old callbacks cannot undo newer state. A rollback to another artifact references its separately admitted release; record actual old identity and invalidate the newer release's confirmation. These are evidence reducers, not remote deployment APIs.

Confirmation uses `release-confirm` for every declared unit. Require source/artifact/configuration and active binding correspondence, safe negative and legitimate positive behavior, fresh timestamps and raw evidence. Missing units remain incomplete; changed source/configuration/artifact, wrong binding or failed behavior cannot pass. Confirmation applies only to the observed scope/time. Local fixture success is not production or a product finding's closure. Any native finding transition remains a separate authorized operation with ticket readback.

Maintenance is explicitly invoked. `release-maintain` compares full source/artifact/configuration/claim/fence/policy identities and evidence freshness, confirms every required unit still has coverage, and treats missing/stopped/rolled-back units as needing re-verification. Empty evidence never earns green. Expiry/drift alone is not a compromise. Confirmed scoped counterexamples produce corrective-work action keys; reconcile existing Linear tickets/PRs before creating any. Retain counterexamples, failed/unsupported runs and complete denominators. The helper returns actions; the invoked agent performs authorized native effects and records readback. Do not open real security findings from synthetic implementation fixtures.

Developers and agents own claims as normal component code. Use the existing repository contribution/CODEOWNERS policy and collective architectural review. Do not create a separate mandatory security-team authority or signer roster. Set definition_review_required only when that actual native policy requires it. Hard-control failures remain visible; ordinary authorized contract edits are not tampering by definition.

Every stage fetches the ticket/resource graph and publishes raw commands, exact subjects, outcomes and remaining scope before the next stage. Generic code never assumes a particular language, application, entry point, service or production adapter. Case-specific release plans and adapters are supplied through verified resources. Source/build/config digests belong in generated receipts, not authored claims.

The actual local reference trial builds a Go binary from a Git archive, starts an owned loopback process, observes its PID and artifact identity, tests positive/negative requests under one configuration, records rollout and confirmation, checks maintenance drift/expiry/deduplication, then terminates/reaps the process. Cleanup is recorded as rollback; the earlier confirmation is no longer current afterwards. This is a framework qualification fixture with no security ticket under review.
