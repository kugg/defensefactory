# Integration: verified candidate to observed integrated revision

Start from the live ticket and immutable verification report/resources, including required obligations, source/claim/evaluator/check versions and explicit policy. Read the actual PR/base/head and check observations using `github-subject`. This is a read-only observation; required context names alone do not prove enforcement or absence of bypass rights. Missing API data is unknown, not protection. A native lifecycle label such as Done is not a candidate verification receipt.

`integration-plan` takes `repo/repository/base/head/method` and computes the prospective merge tree from exact commits. It materializes a deterministic local preview commit for evaluation without moving a branch. Merge conflicts produce no runnable preview. The object is not an integrated revision. Supported strategies are two-parent merge and one-parent squash. Rebase requires a separate correspondence policy and is rejected here.

`integration-assess` takes the plan, verified verification-stage report, fresh platform observation, case/actor and invoker-supplied policy. `policy.integration_cases[case]` binds repository/PR, demo or protected mode, merge strategy, approved verification-contract hash (including scope/guidance), claim/evaluator/check digests, required platform checks and optional app/review identity. An empty platform-check list requires an explicit reason. Observations bind checks to the head SHA; a newer failure/pending run cannot hide behind old green output. Wrong app, old head, draft/closed PR, unknown mergeability, incomplete lookup, stale/future observation, changed base/head, changed specification/scope or incomplete/contradictory underlying verification blocks admission. `max_observation_age_seconds` comes from policy.

Normally execute verification on `evaluation_revision`. Source-level evidence may be reused from the PR head only when the entire merge tree equals the verified candidate tree, policy explicitly selects `reuse_mode: exact_tree`, and `revision_sensitive: false`. Commit-sensitive generated/build/index/model evidence cannot inherit this rule. A changed base that changes the tree requires new verification even if the candidate's own checks were green. Claim/evaluator/check digests remain mandatory. The helper re-derives the plan from actual Git objects and validates preview parents/tree.

The trusted invoker explicitly selects `mode: demo` for the authorized same-host rehearsal. It never claims protected independent acceptance. `mode: protected` still requires existing authenticated, isolated-verifier and repository-protection admission; missing trust cannot fall back to demo. Policy is provisioned by the environment, not accepted from a patch or ticket prose merely because a field is populated. Hash checks do not authenticate a policy author or establish OS isolation.

Successful admission does not authorize a merge. `merge-intent` additionally checks the actor's merge grant, existing user/policy authorization reference, unchanged policy and verification identities, and a fresh repeated admission. It returns a bound effect key and expected base/head/strategy only; it calls no remote merge API. If an actual merge is already authorized, use the connector/CLI's expected-head precondition and governing repository gates; never bypass them with admin/force. This implementation task itself does not authorize a product merge. Do not add another user approval when existing authorization already covers the action.

After a timeout, inspect the actual PR before retrying. `merge-reconcile` checks a fresh observation against the same intent/policy. A merged PR is accepted as an integrated source only after its real commit exists locally and its tree and direct parents match the admitted plan. It emits the actual integrated SHA, not the synthetic preview SHA. A squash may have a different commit ID with identical admitted tree and expected base parent. An already merged effect is recorded once rather than merged again. Open unchanged PRs require a refreshed intent before retry; closed, moved, unknown, stale or mismatched outcomes stop. Missing objects require an authorized fetch then reconciliation, not an invented receipt.

Readback and merge are not a distributed transaction. Expected-head protects only the head; the base can still move between reads and mutation. Strict platform policy and final actual-tree/parent confirmation remain necessary. A mismatching actual merge is retained as an integration failure and cannot advance to build/deployment. These helpers do not guarantee that an external actor cannot perform a bad merge.

Publish the plan, policy identity, verification reference, observations, admissions, retained failures, intent and actual integration receipt through the ticket. Verify fresh resource bytes/readback before any build. Merge-only success never closes a finding: identified artifact build, rollout/configuration scope and deployed confirmation follow in later stages.
